Task: BE-01.16 — DLQ and retry policy (bounded retries, poison queue, idempotent handlers)

Context
- Make message handling resilient with bounded retries and a Dead Letter Queue (DLQ). Use idempotency keys to avoid duplicate side effects. Classify errors (retryable vs non-retryable) and include `correlationId` in envelopes.

Files
- packages/events/src/topics.ts (add DLQ topic names)
- apps/orchestrator/src/index.ts (publish/consume policies)
- docs/EVENTS.md (reference, document DLQ contracts)
 - packages/events/src/contracts/envelope.ts (ensure metadata fields available)

Steps
1) Define DLQ topics for orchestrator-related streams (e.g., `triage.input.dlq`). Update `Topics` enum and document payload envelope in `docs/EVENTS.md`.
2) Classify errors: add a typed `RetryableError` vs `NonRetryableError`. Only retry on retryable with exponential backoff and jitter, max N attempts (e.g., 3).
3) On max retries exceeded or non-retryable error, publish to DLQ with metadata: `originalTopic`, `attempts`, `correlationId`, `errorCode`, `reason`.
4) Ensure idempotency: include an idempotency key in message headers/body; consumers reject duplicates using `IdempotencyStore` (see BE-01.6).
5) Add a simple DLQ handler stub that logs safely and exposes metrics (`dlq.count`, `retry.attempts`).
 6) Include a redelivery delay strategy (dead-letter with visibility timeout or scheduled retry topic) to avoid hot-looping.

Acceptance Criteria
- Topics include DLQ variants; envelopes contain required metadata.
- Retry policy bounded and jittered; DLQ receives poison messages deterministically.
- Idempotent consumers; duplicates are detected and ignored with metrics.

Validate
- Simulate a retryable failure and observe 3 attempts then DLQ; simulate non-retryable and immediate DLQ.
 - Verify idempotency key suppresses duplicate processing upon redelivery.
