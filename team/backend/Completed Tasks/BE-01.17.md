Task: BE-01.17 — Rate limiting & abuse protection

Context
- Protect the orchestrator from abusive or accidental high-rate traffic. Apply per-tenant/token bucket limits and return standard 429 envelopes. Ensure limits are configurable and observable.

Files
- apps/orchestrator/src/index.ts (ingress limiter)
- @onecare/config (rate limit config)
 - apps/orchestrator/src/application/error.ts (reuse envelope)

Steps
1) Implement an in-memory token bucket with configurable `capacity`, `refillPerSecond`, and keying by tenant/account or API key. Default conservative limits.
2) On rate exceed, return 429 with `{ error: { code: 'rate_limited', correlationId } }`. Include `Retry-After` header when possible.
3) Emit metrics: `ratelimit.exceeded`, `ratelimit.allowed`; include labels for tenant and endpoint. Do not log PHI.
4) Expose minimal admin debug endpoint to query current limiter stats (guarded, dev-only). Prevent exposing tenant keys.
5) Add unit tests for limit behavior across tenants and burst scenarios.

Acceptance Criteria
- Enforced 429 response on exceed with envelope and headers; limits configurable per-tenant.
- Deterministic tests for burst and refill behavior; metrics present.

Validate
- Fire bursts with autocannon targeting `/safety-check` and confirm 429s start after configured tokens are consumed.
